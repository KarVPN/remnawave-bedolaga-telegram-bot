# Фильтры и массовые действия в Users

## Доступ и совместимость

Новый интерфейс рассчитан на API Bedolaga v5 и Remnawave 3. Для журнала,
предпросмотра, запуска, продолжения, отмены и SSE требуются **оба** разрешения:
`users:read` и `bulk_actions:execute`. Обычное чтение Users по-прежнему требует
только `users:read`. Список восстановления показывает последние 10 подтверждённых
операций автора, сначала незавершённые; черновики выборок туда не попадают.
Администратор с обоими разрешениями может продолжить известную ему операцию
другого администратора. Автор операции сохраняется в журнале.

Разворачивать сначала backend с миграцией **0132**, затем frontend. Старый
`POST /cabinet/admin/bulk/execute` и его SSE остаются совместимыми; в его enum
добавлен `deduct_days` с положительным `params.days`. Новый журнал используется
только новым API `/cabinet/admin/user-bulk-operations` и не восстанавливает старые
операции, выполненные до его появления. PostgreSQL обязателен для запуска:
SQLite не обеспечивает используемую межпроцессную блокировку.

## Что означает дата

Фильтр «Подписка пересекала дату (по текущим срокам)» — **оценка, а не
подтверждённая история активности**. День задан в `settings.TIMEZONE`; локальные
полночь выбранного дня и следующего дня переводятся в UTC отдельно. Это учитывает
дни с переходом DST. SQL проверяет `start_date < конец_дня AND end_date > начало_дня`.
Истёкший сейчас статус не исключает пересечение в прошлом. Пользователь появляется
один раз через `EXISTS`, даже если подходят несколько подписок; их ID показаны
в строке списка. Список, счётчик и серверная фиксация используют общий SQL-предикат.

`SubscriptionEvent` содержит события покупок, продлений и другие уведомления,
но не полный непрерывный журнал изменений статуса и прежних сроков. Он не даёт
надёжно восстановить все интервалы активности после отмен, продлений и бэкапов.
Поэтому недостающие события не достраиваются, текущие сроки не выдаются за историю.
В интерфейсе постоянно виден текст об ограничении. Для подтверждённой исторической
выборки сначала нужен отдельный источник полных интервалов активности.

## Какие подписки меняются

- Выбор страницы сохраняется при переходе на другую страницу. Изменение поиска,
  фильтра или сортировки сбрасывает выбор. Общий чекбокс имеет промежуточное состояние.
- «Выбрать всех по текущим фильтрам» сразу сохраняет на сервере конкретные пары
  `user_id / subscription_id`, включая пропуски без подписки. В браузер возвращаются
  только идентификатор операции и агрегаты. Новые пользователи и подписки в эту
  выборку не добавляются. Изменение действия копирует зафиксированные цели,
  пересчитывая применимость, а не делает новый поиск по базе.
- При нескольких подписках обрабатываются **все подходящие подписки**. Фильтры
  даты, статуса подписки и ближайшего окончания ограничивают подписки-цели.
  Ручной выбор пользователей передаёт те же фильтры. Нет случайного выбора первой.
- Если нет подходящей подписки, пользователь пропускается. Нет закреплённого
  `subscription.remnawave_id` — подписка пропускается: новый путь не подставляет
  чужой/пользовательский аккаунт панели вместо идентичности выбранной подписки.
- При удалении или смене владельца подписки после предпросмотра цель пропускается.
  Применимость проверяется снова перед обработкой; точные числа подтверждения
  относятся к моменту предпросмотра, последующие изменения могут увеличить пропуски.
- Подтверждение привязано к сохранённому ID операции и неизменяемым параметрам.
  Уникальный `request_key` защищён ограничением БД на пару «автор / ключ»;
  повтор с другим содержимым получает 409. Повтор `/run` не повторяет обработанные цели.

## Семантика действий

**10 / 50 / 100 GB.** Используется существующий `_do_add_traffic`: пакет
`TrafficPurchase` действует 30 дней, увеличиваются лимит и счётчик докупленного
трафика. Безлимит (`traffic_limit_gb <= 0`) пропускается. Существующий
`reactivate_subscription` может активировать `disabled`, `expired`, `limited`,
если `end_date` ещё в будущем; истёкшее время от начисления не продлевается.
Следует синхронизация и существующая команда включения аккаунта панели.

**Продление на N дней.** Используется `_do_extend_subscription` и
`extend_subscription`: для ещё действующего срока дни добавляются к окончанию,
для истёкшего — к текущему времени. Существующие правила реактивации, обработки
грейса и пакетов трафика сохраняются. Положительное продление переводит
`expired / disabled / limited / trial` в `active`; для `pending` это не обещается.
Платная конвертация триала без указания тарифа не выполняется.

**Сокращение на N дней.** В существующий dispatcher добавлен `deduct_days`.
Положительное N передаётся как отрицательное значение в уже имеющуюся ветку
`extend_subscription`, то есть вычитается из текущего окончания. Если новый срок
прошёл, записывается `expired`, синхронизация отключает доступ в панели. Дата
окончания и статус не восстанавливаются при отмене операции.

В новом журналируемом пути ошибка или пропуск синхронизации, а также неуспешная
команда включения панели не считаются успехом. Старые вызовы сохраняют прежнюю
обработку ошибок; строгий режим ограничен контекстом новой операции.

## Журнал, прогресс и восстановление

`user_bulk_operations` хранит автора, ключ повтора, действие, параметры, состояние
и времена. `user_bulk_targets` хранит каждую зафиксированную цель, статус,
сообщение и время результата. PostgreSQL — источник истины; Redis не нужен.
Счётчики вычисляются SQL-агрегациями из журнала. Пользователь обработан только
после завершения всех его целей. Отдельно показаны подписки, частичные успехи,
пропуски, отмены и неопределённые исходы. Ошибки выдаются страницами по 50 элементов.

Перед вызовом обработчика цель фиксируется как `processing` отдельным commit.
После подтверждённого успеха — `success`. CRUD может коммитить изменения до
обращения к Remnawave; ошибка API не доказывает отсутствия изменений. Поэтому
ошибка выполнения и `processing`, оставшийся после сбоя, получают **`uncertain`**
(«Результат требует проверки»), а не автоматически повторяются. Успешные и
неопределённые цели не становятся `pending` при продолжении. Проверять такие
подписки нужно вручную в БД и панели; API автоматического повторного начисления
или разрешения неопределённого результата намеренно нет.

Одна PostgreSQL advisory-блокировка на выделенном соединении допускает только
одну пачку во всех процессах. Она переживает commit внутри бизнес-обработчиков.
Конкурирующий запуск получает 409. После получения освободившейся блокировки
можно безопасно признать оставшиеся `processing` прерванными. GET состояния
восстанавливает такое состояние, а изменения выполняются только явным `/run`.

Браузер последовательно запрашивает пачки, пока открыт Users. По умолчанию
`USERS_BULK_BATCH_SIZE=25` (1–100), `USERS_BULK_ITEM_DELAY=0.5` секунды (0.1–10).
Если закрыть страницу или потерять соединение, следующие пачки автоматически
не запускаются; текущая может завершиться. После возвращения — явное «Продолжить».
На неопределённом результате автоматическая цепочка пачек останавливается.
Существующий Remnawave API-клиент ограничивает частоту, делает ограниченные повторы
с задержкой и общей паузой по `429 / Retry-After`. Повтор локального начисления
в новом журнале не выполняется; после исчерпания повторов запрос требует проверки.

SSE `/events` использует типы `progress / complete` существующего bulk-протокола,
но читает постоянный журнал с интервалом две секунды. Поток закрывается на
`completed / cancelled / needs_review`. Для nginx отключить буферизацию SSE;
таймаут `/run` должен позволять закончить небольшую пачку, включая штатные повторы
API-клиента. Таймаут прокси сам по себе не повод создавать новую операцию:
обновить состояние существующей и продолжить её после завершения текущей пачки.

«Отменить оставшихся» помечает только `pending` как `cancelled`. Проверка отмены
и захват очередной цели сериализуются блокировкой строки операции. Запрос к панели,
уже отправленный для `processing`, не отзывается. Выполненные изменения сохраняются.
Откат, компенсации и снимки прежних значений не реализованы.

## Проверка на стенде

1. Использовать отдельные PostgreSQL и Remnawave со стендовыми аккаунтами, выполнить
   миграции штатным запуском backend, проверить ревизию 0132. Не использовать продакшен.
2. Подготовить пользователя без подписки, с безлимитом, с двумя подписками,
   `limited`, `disabled`, с истёкшим сроком и с действующим сроком.
3. Проверить фильтр даты около полуночи TIMEZONE, поиск, счётчик, несколько страниц
   и ID подходящих подписок. Зафиксировать «все», добавить нового пользователя:
   он не должен попасть в подтверждение старой выборки.
4. На отдельных выборках проверить 10/50/100 GB, продление и сокращение. Сверить
   `TrafficPurchase`, даты/статусы и выбранные аккаунты панели, в том числе реактивацию.
5. Запустить больше одной пачки, отменить во время запроса, убедиться, что следующий
   элемент не стартовал. Уже выполненные изменения должны сохраниться.
6. Перезапустить backend после фиксации `processing`, вернуться в Users. Подтверждённые
   успехи не повторяются; прерванная цель требует проверки; «Продолжить» обрабатывает
   только `pending`. Попробовать продолжить двумя администраторами одновременно.
7. Имитировать 429, таймаут и недоступность панели. Проверить ограниченные повторы
   существующего API-клиента, остановку цепочки и отсутствие повторного локального
   начисления. Восстановить панель, проверить неопределённые результаты вручную.
8. Проверить роли только с `users:read`, только с `bulk_actions:execute`, с обоими.
   Новый журнал и все действия должны требовать оба разрешения.

Автотесты: `pytest tests/cabinet/test_user_bulk_operations*.py`, плюс существующие
тесты фильтров и bulk. Проверки с меткой `postgres` требуют отдельную тестовую БД
`TEST_DATABASE_URL`; `REQUIRE_POSTGRES_TESTS=1` запрещает молчаливые пропуски. В них
проверены конкурентность, отмена, перезапуск, commit до сбоя API, миграция и SQL-снимок
3000 пользователей. Браузерные сценарии находятся в frontend PR.
